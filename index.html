⏱️ קריאת המבוא והדגמת מעגל החיים: כ-60 דק'

מסיבת אוזניות (Silent Disco) היא מסיבה בלי רמקולים: כולם שומעים את אותה מוזיקה, אבל כל אחד באוזניות של עצמו. באפליקציה שתבנו, משתמש אחד הוא הדי-ג'יי והשאר הם משתתפים. הדי-ג'יי בוחר שיר, לוחץ Play – והשיר מתחיל להתנגן באותו רגע ובאותה נקודה בכל הטלפונים המחוברים לחדר, גם כשהמסך כבוי והטלפון בכיס. בנוסף הדי-ג'יי יכול לשלוח הודעות שמופיעות כהתראה אצל כולם, ולכל המשתתפים יש מסך משותף עם תגובות חיות, שיתוף תמונות, מפה של מתחם המסיבה ובוט עזרה חכם.

שלוש הבעיות הקשות

  1. לגרום להרבה טלפונים לנגן יחד. ההודעה מהשרת לא מגיעה לכל הטלפונים באותו רגע, וגם השעון הפנימי של כל טלפון קצת שונה. לכן אם נשדר את הפקודה "כולם תנגנו עכשיו" – נשמע הד, כי כל אחד יתחיל בזמן מעט אחר. הפתרון הוא לא לשלוח פקודה, אלא לתאר את המצב: "השיר הזה, התחיל ברגע הזה לפי שעון השרת". כל טלפון מחשב לבד לאיזו נקודה בשיר עליו לקפוץ, וכך כולם מגיעים לאותו מקום.
  2. לא מספיק להסתיר כפתור. קל להסתיר מהמשתתף את כפתור "החלף שיר", אבל הסתרה איננה אבטחה. מי שמבין קצת בתכנות יכול לשלוח פקודה לבסיס הנתונים בלי לעבור דרך המסך שלנו בכלל, ולהשתלט על המסיבה. לכן ההגבלה חייבת לשבת אצל השרת ולא באפליקציה – בקובץ כללים שנכתוב בשלב 18.
  3. מוזיקה שממשיכה כשהמסך כבוי. אנדרואיד סוגר מסכים שאינם גלויים כדי לחסוך בסוללה. נגן שחי בתוך מסך יושתק תוך שניות מרגע שהטלפון נכנס לכיס. הפתרון הוא להעביר את הנגן לשירות רקע – רכיב שרץ בנפרד מהמסך ומציג התראה קבועה שמסמנת למערכת "אני עסוק, אל תסגור אותי".

שאלה ראשונה: למה בכלל צריך "מסד נתונים"? ⏱️ 15 דק'

בואו נחשוב רגע בלי מילים מקצועיות. הדי-ג'יי לחץ על שיר. עכשיו שלושים טלפונים אחרים צריכים לדעת על זה. איך הם ידעו?

התשובה הכי טבעית היא "שהטלפון של הדי-ג'יי יספר להם". אבל נסו לחשוב מה זה דורש: הטלפון של הדי-ג'יי צריך להכיר את שלושים הטלפונים, לדעת את הכתובת של כל אחד, ולשלוח לכל אחד מהם הודעה בנפרד. ואם אחד מהם היה בדיוק במעלית בלי קליטה? ואם מישהו חדש הצטרף אחרי שהשיר התחיל, למי הוא יפנה כדי לגלות מה מתנגן?

שאלה שנייה: למה הלוח צריך להיות מקוון? ⏱️ 10 דק'

אפשר לשמור מידע גם בתוך הטלפון עצמו, וזה מה שנעשה בשלב 5 כשנשמור את השם של המשתמש. אבל מידע שנשמר בטלפון שלי הוא שלי בלבד ואף אחד אחר לא רואה אותו. הוא כמו פתק שכתבתי לעצמי במגירה.

במסיבה שלנו כל המידע הוא מידע משותף: מה מתנגן, מי נמצא בחדר, מה כתבו בפיד. לכן הלוח לא יכול לשכון בתוך אחד הטלפונים אלא צריך לשבת במקום שכולם מגיעים אליו – כלומר במחשב באינטרנט, שנקרא שרת. זה מה שהמילה "מקוון" אומרת: המידע לא נמצא אצלי, הוא נמצא במקום מרכזי וכולנו פונים אליו דרך הרשת.

יש לזה עוד יתרון חשוב: המידע שורד. אם הטלפון של הדי-ג'יי נפל, נכבה או נגמרה לו הסוללה, הלוח באינטרנט ממשיך להתקיים עם כל מה שכתוב עליו. אם הלוח היה בתוך הטלפון שלו, המסיבה כולה הייתה נעלמת יחד איתו.

השירות שנשתמש בו נקרא Firebase, והוא של גוגל. הוא נותן לנו בחינם גם את הלוח המשותף וגם מקום לשמור בו תמונות. איך הוא עובד בפועל, ומה בדיוק כותבים לתוכו – נלמד בשלב 1 ובשלבים שאחריו. בשלב הזה מספיק שתבינו למה אנחנו צריכים אותו.

מושג מקדים: מה זה "מסך" באנדרואיד, ומהו מעגל החיים שלו ⏱️ 25 דק'

כל מסך באפליקציית אנדרואיד הוא מחלקה בג'אווה שנקראת Activity. באפליקציה שלנו יהיו שלושה מסכים כאלה: מסך הפתיחה, המסך הראשי ומסך המסיבה.

והנה ההבדל הגדול מתוכנית ג'אווה רגילה שכתבתם עד היום. בתוכנית רגילה אתם קוראים לפונקציות: יש main, הוא רץ מלמעלה למטה, ונגמר. באנדרואיד זה הפוך: המערכת קוראת לכם. אתם כותבים פונקציות מוכנות, והמערכת מפעילה אותן ברגעים שהיא מחליטה – כשהמסך נפתח, כשהמשתמש עבר לוואטסאפ, כשהוא חזר. הפונקציות האלה נקראות מתודות מעגל החיים (lifecycle methods).

למה זה קיים בכלל? כי בטלפון, בשונה ממחשב, יש סוללה אחת ומעט זיכרון. המערכת חייבת להיות חופשית לעצור מסך שהמשתמש לא מסתכל עליו. כדי שהיא תוכל לעשות זאת בלי להרוס לנו את האפליקציה, היא מודיעה לנו מראש בכל שינוי, ואנחנו מגיבים.

הדגמה: תריצו את זה ותראו במו עיניכם

זו לא תיאוריה. הדביקו את הקוד הבא ב-MainActivity של הפרויקט הריק שיצרתם, הריצו, ופתחו למטה ב-Android Studio את חלון Logcat עם סינון למילה LIFECYCLE. עכשיו שחקו עם הטלפון: לחצו על כפתור הבית, חזרו לאפליקציה, סובבו את המסך – ותראו את ההודעות מופיעות בזמן אמת. כך תרגישו את מעגל החיים במקום לשנן אותו.

MainActivity.java (הדגמה זמנית) 
package com.example.laparty;

import android.os.Bundle;
import android.util.Log;

import androidx.appcompat.app.AppCompatActivity;

/**
 * A temporary demo, only to SEE the lifecycle in Logcat.
 * Filter Logcat by the word LIFECYCLE and play with the phone.
 */
public class MainActivity extends AppCompatActivity {

    private static final String TAG = "LIFECYCLE";

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);          // always call super FIRST
        setContentView(R.layout.activity_main);
        Log.d(TAG, "onCreate  - the screen is being built");
    }

    @Override
    protected void onStart() {
        super.onStart();
        Log.d(TAG, "onStart   - the screen became visible");
    }

    @Override
    protected void onResume() {
        super.onResume();
        Log.d(TAG, "onResume  - the screen is in front, reacting to touches");
    }

    @Override
    protected void onPause() {
        super.onPause();
        Log.d(TAG, "onPause   - something covered me, I am losing focus");
    }

    @Override
    protected void onStop() {
        super.onStop();
        Log.d(TAG, "onStop    - I am no longer visible at all");
    }

    @Override
    protected void onDestroy() {
        super.onDestroy();
        Log.d(TAG, "onDestroy - goodbye, this screen is being destroyed");
    }
}

שני דברים שכדאי לשים לב אליהם בקוד

  • @Override – מודיע למהדר "אני דורס מתודה שכבר קיימת במחלקת האב". אם תכתבו בטעות onCreat, המהדר יצעק במקום שהאפליקציה תתנהג מוזר.
  • super.onCreate(...) – קריאה למתודה של מחלקת האב. בלעדיה אנדרואיד לא יבצע את ההכנות הפנימיות שלו והאפליקציה תקרוס. תמיד קוראים ל-super ראשון (ובמתודות הסיום נהוג לקרוא לו ראשון גם כן).
  • Log.d(TAG, "...") – הדפסה לחלון Logcat. זו שיטת האיתור המרכזית שלכם בכל הפרויקט: היא מראה מה קרה בפועל, במקום לנחש.

את הקוד הזה נמחק בשלב 4 כשנבנה את המסך הראשי האמיתי. כרגע הוא קיים רק כדי להדגים. בשלב 3 נשתמש ב-onCreate וב-onDestroy באמת – ואז זה יהיה מוכר לכם.

שלב 1: תכנון וארכיטקטורה ⏱️ סה"כ כ-90 דק'

רגע, מה זה בכלל "ארכיטקטורה"?

בדיוק כמו בבניין. לפני שיוצקים בטון, האדריכל מחליט כמה חדרים יהיו, מי מחובר למי ואיפה עוברים הצינורות. ארכיטקטורה של תוכנה זה בדיוק אותו דבר: החלטה מראש מאילו חלקים האפליקציה מורכבת, מה כל חלק אחראי עליו, ואיך החלקים מדברים ביניהם.

בשלב הזה לא כותבים קוד. מציירים על דף. זה נשמע מיותר, אבל זה השלב שחוסך את מרבית הסבל בהמשך.

למה ככה? למה לא פשוט להתחיל לתכנת?

כי יש הבדל עצום בין שני סוגי טעויות. אם קראתם למשתנה בשם לא מוצלח – משנים אותו בשנייה. אבל אם סידרתם את המידע בצורה לא נכונה, וגיליתם את זה אחרי שכתבתם עשרה מסכים שכולם קוראים את המידע הזה – אתם מוחקים ימי עבודה.

יש עוד סיבה, וזאת חשובה במיוחד לפרויקט שלנו. בשלב 18 נכתוב כללי אבטחה – חוקים שאומרים "המשתתף הרגיל לא רשאי להחליף שיר, רק הדי-ג'יי". החוקים האלה נכתבים לפי המקום שבו המידע יושב. אם נערבב במקום אחד מידע שרק הדי-ג'יי רשאי לשנות עם מידע שכולם רשאים לשנות – לא נוכל להגן על כלום. לכן מהרגע הראשון נפריד את המידע לפי מי מורשה לשנות אותו.

מה עושים בשלב הזה

  3. כותבים ארבע השורות שיכולות להיות "מה קורה במסיבה עכשיו", ומי רשאי לשנות את השורה הזאת.

צעד 3: תזכורת – מפתח וערך (HashMap)

אתם מכירים מערך: names[0], names[1]. הגישה היא לפי מספר. אבל מה אם אני רוצה לשמור גיל לפי שם? למשל "מאיה = 17". בג'אווה יש לזה מבנה שנקרא HashMap, ובו כל פריט הוא זוג: מפתח (key) וערך (value).

HashMap – תזכורת מג'אווה 
// An array is accessed by a NUMBER:
String[] names = {"Roni", "Maya"};
String first = names[0];              // "Roni"

// A HashMap is accessed by a KEY of our choosing:
HashMap<String, Integer> ages = new HashMap<>();
ages.put("Maya", 17);                 // key = "Maya",  value = 17
ages.put("Roni", 18);

int mayaAge = ages.get("Maya");       // 17  -- no need to know any index

// The big advantage: instant access by name, no searching.
// This is EXACTLY how the party database is built:
//    key = the room code "4821"  ->  value = everything about that room

למה זה קריטי לנו? כי במסיבה שלנו נרצה לשאול "תן לי את חדר 4821" ולא "תן לי את החדר החמישי ברשימה". המפתח הוא קוד החדר, בדיוק כמו מפתח ב-HashMap.

צעד 4: איך כותבים את זה על דף – JSON

JSON היא צורה לכתוב HashMap בתוך קובץ טקסט, כדי שאפשר יהיה לשלוח אותו ברשת. זה כל הסיפור. הכללים בו קצרים: סוגריים מסולסלים { } פותחים אוסף של זוגות, כל זוג נכתב "מפתח": ערך, ופסיק מפריד בין זוגות. היתרון: אדם יכול לקרוא את זה בעיניים, וגם המחשב מבין את זה.

אותו מידע בדיוק – בג'אווה מול JSON 
// ---- In Java (in memory) ----
HashMap<String, Object> maya = new HashMap<>();
maya.put("name", "Maya");
maya.put("age", 17);
maya.put("online", true);


// ---- The same thing written as JSON (as text, sendable over the network) ----
{
  "name": "Maya",
  "age": 17,
  "online": true
}


// ---- And a value can itself be another collection. That is how a TREE is built ----
{
  "participants": {
    "77b0e4aa": { "name": "Maya", "age": 17 },
    "a3f9c1d2": { "name": "Roni", "age": 18 }
  }
}
// Reading it out loud: inside "participants" there are two keys.
// Each key is a person's id, and its value is that person's details.

ולכן: איך ייראה הלוח המשותף שלנו?

הלוח כולו יהיה קובץ JSON אחד גדול שיישב בשרת. הוא בנוי כמו עץ תיקיות במחשב: אוסף בתוך אוסף, ובקצה תמיד יושב ערך פשוט – טקסט, מספר או כן/לא. כל "תיקייה" כזאת נקראת צומת (node), ולכל צומת יש כתובת מלאה בדיוק כמו נתיב של קובץ: rooms/4821/meta/djName.

הכתובת הזאת היא מה שנכתוב בקוד כשנרצה לקרוא או לשנות פרט מסוים, וגם מה שנגן עליו בכללי האבטחה בשלב 18.

מה חשוב להבין לפני ההרצה?

  • צומת (node) – "תיקייה" בעץ המידע שעל הלוח המשותף. הכתובת המלאה שלה נראית כמו נתיב קובץ: rooms/4821/track.
  • startedAtServer – הרגע שבו השיר התחיל, לפי שעון השרת ולא לפי השעון של הטלפון. לכל טלפון יש שעון קצת אחר, ולכן צריך שעון אחד משותף שכולם מודדים לפיו. זה הבסיס לכל הסנכרון בשלב 10.
  • participants/<id> – שם הצומת הוא המזהה (uid) שהמשתמש קיבל מ-Firebase Auth בשלב 5, ולא מספר רץ. רק ככה אפשר יהיה לכתוב את החוק "כל אחד נוגע רק בעצמו", כי רק מזהה שהשרת עצמו חילק הוא מזהה שהשרת יכול לאמת.
  • ארבע התשובות – LOBBY, PLAYING, PAUSED, ENDED. אלה כל האפשרויות, וכל אחת דורשת מהאפליקציה התנהגות אחרת. לכן זו מילה מרשימה סגורה ולא "כן/לא".
  • עץ שטוח עדיף על עץ עמוק – ב-Realtime Database, כשקוראים צומת מקבלים גם את כל מה שמתחתיו. אם נקנן הכול עמוק, כל קריאה קטנה תוריד המון מידע מיותר ותבזבז סוללה וחבילת גלישה.

למה ככה?

Firebase מחזיר JSON. אפשר לקרוא אותו כ-HashMap ולגשת לשדות במפתחות טקסט, אבל אז כל שגיאת כתיב מתגלה רק בזמן ריצה. במקום זה נשתמש ב-POJO (Plain Old Java Object) – מחלקה פשוטה עם שדות ו-getters/setters. הספרייה יודעת לקרוא getName() ולכתוב "name", ובכיוון ההפוך לקרוא snapshot.getValue(Participant.class). כך המהדר בודק בשבילנו את שמות השדות.

הדרישה הקריטית: constructor ריק. Firebase יוצר את האובייקט באמצעות reflection – היא קוראת ל-constructor בלי פרמטרים ואחר כך מזריקה את השדות דרך ה-setters. בלי constructor ריק תקבלו קריסה עם ההודעה does not define a no-argument constructor. ברגע שאתם מוסיפים constructor עם פרמטרים, Java מפסיקה לספק את הריק אוטומטית – ולכן תמיד כותבים את שניהם.

package com.example.laparty.model;

/**
 * The two roles in a party.
 * Stored in the database as a String ("DJ" / "PARTICIPANT"),
 * because Firebase cannot serialize a Java enum by itself.
 */
public enum Role {
    DJ,
    PARTICIPANT;

    /** Safe conversion from the database value back to an enum. */
    public static Role fromString(String value) {
        if (value == null) {
            return PARTICIPANT;
        }
        try {
            return Role.valueOf(value);
        } catch (IllegalArgumentException e) {
            // Unknown value in the database - never crash the app for it
            return PARTICIPANT;
        }
    }
}

package com.example.laparty.model;

/**
 * The single source of truth for "what should be playing right now".
 * Only the DJ writes this node; every participant only reads it.
 */
public class Track {

    public static final String STATE_PLAYING = "PLAYING";
    public static final String STATE_PAUSED  = "PAUSED";

    private String url;
    private String title;
    private String state;            // PLAYING | PAUSED
    private long   positionMs;       // position inside the song at startedAtServer
    private long   startedAtServer;  // SERVER time, not device time

    /** Required by Firebase - do not delete. */
    public Track() {
    }

    public Track(String url, String title, String state, long positionMs, long startedAtServer) {
        this.url = url;
        this.title = title;
        this.state = state;
        this.positionMs = positionMs;
        this.startedAtServer = startedAtServer;
    }

    public String getUrl() { return url; }
    public void setUrl(String url) { this.url = url; }

    public String getTitle() { return title; }
    public void setTitle(String title) { this.title = title; }

    public String getState() { return state; }
    public void setState(String state) { this.state = state; }

    public long getPositionMs() { return positionMs; }
    public void setPositionMs(long positionMs) { this.positionMs = positionMs; }

    public long getStartedAtServer() { return startedAtServer; }
    public void setStartedAtServer(long startedAtServer) { this.startedAtServer = startedAtServer; }

    public boolean isPlaying() {
        return STATE_PLAYING.equals(state);

מושג מקדים: מה זה thread? ⏱️ 20 דק'

thread (נקרא "תהליכון" או "חוט ביצוע") הוא פס ייצור אחד שמבצע פקודות אחת אחרי השנייה. עד היום כתבתם תוכניות עם פס ייצור אחד: הפקודות רצו לפי הסדר, כל פקודה חיכתה שקודמתה תסתיים.

באנדרואיד יש פס ייצור מיוחד אחד שנקרא ה-thread הראשי. הוא זה שמצייר את המסך וקורא ללחיצות שלכם. עכשיו חשבו רגע: אם ניתן לפס הייצור הזה מטלה שלוקחת שנייה וחצי, מי יצייר את המסך בזמן הזה? אף אחד. המסך יקפא.

ONE thread (what you know) TWO threads (what we need here) main: [draw][draw][SLEEP 1.5s][draw] main: [draw][draw][draw][draw][draw] ^^^^^^^^^^^ (never blocked, stays smooth) screen frozen! worker: [SLEEP 1.5s] --> "done!" the user sees a stuck app (blocking is fine here)

ומה זה ANR?

ANR = Application Not Responding, כלומר "האפליקציה לא מגיבה". זו הודעה שאנדרואיד עצמו מציג למשתמש כשה-thread הראשי תקוע יותר מכ-5 שניות, עם הצעה לסגור את האפליקציה בכוח. זו החוויה הגרועה ביותר שאפשר לתת למשתמש.

רוצים לראות ANR במו עיניכם? הוסיפו זמנית לתוך onCreate את השורה Thread.sleep(10000); (בתוך try-catch), הריצו, ונסו ללחוץ על המסך. תקבלו אפליקציה קפואה ואחריה הודעת מערכת. מחקו את השורה מיד אחר כך – עשינו את זה רק כדי להרגיש למה שאר השלב הזה קיים.

למה ככה?

מהמושגים למעלה נובעות שתי מסקנות, ושתיהן ביחד מסבירות את הקוד של השלב:

  1. ההמתנה חייבת לקרות ב-thread אחר, אחרת המסך קופא ובמקרה גרוע נקבל ANR.
  2. אבל אסור לגעת במסך מ-thread אחר. זה חוק ברזל באנדרואיד: כל שינוי של View חייב לקרות ב-thread הראשי, אחרת נקבל קריסה בשם CalledFromWrongThreadException. הסיבה: אם שני פסי ייצור יציירו את אותו מסך בו-זמנית, התוצאה בלתי צפויה.

שני החוקים האלה נראים סותרים, ולכן קיימת runOnUiThread(): מחכים ברקע, וכשמסיימים מבקשים מה-thread הראשי לבצע את השינוי במסך. זו התבנית שתחזור בכל הפרויקט, ובגדול היא כל מה שצריך לזכור מהשלב הזה.

גילוי נאות חשוב: למשימה הזאת דווקא, Handler.postDelayed() היא הדרך הנכונה באנדרואיד – שורה אחת, בלי ליצור thread, והשעון מנוהל על ידי המערכת. אנחנו כותבים כאן גם את גרסת ה-Thread הגלמית כתרגיל למידה, כדי שתפגשו InterruptedException ותבינו את המודל. thread גלמי באמת נחוץ כשיש עבודה ארוכה וחוסמת – למשל קריאת רשת לבוט ה-AI בשלב 17, ושם נחליף אותו ב-Executor שמנהל בריכת threads במקומנו.

package com.example.laparty;

import android.content.Intent;
import android.os.Bundle;
import android.util.Log;

import androidx.appcompat.app.AppCompatActivity;

/**
 * Splash screen.
 *
 * NOTE: we use a raw Thread here on purpose, as a learning exercise.
 * The idiomatic Android way for a simple delay is:
 *
 *     new Handler(Looper.getMainLooper()).postDelayed(this::goToMain, SPLASH_DELAY_MS);
 *
 * A raw Thread is really needed only for long blocking work,
 * such as the network call to the AI bot in step 17.
 */
public class SplashActivity extends AppCompatActivity {

    private static final String TAG = "SplashActivity";
    private static final long SPLASH_DELAY_MS = 1500;

    /** Kept so we can interrupt the waiting thread if the user leaves early. */
    private Thread splashThread;

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        setContentView(R.layout.activity_splash);

        splashThread = new Thread(new Runnable() {
            @Override
            public void run() {
                // We are NOT on the UI thread here - blocking is allowed.
                try {
                    Thread.sleep(SPLASH_DELAY_MS);
                } catch (InterruptedException e) {
                    // Someone called interrupt() on us, most likely because
                    // the activity is being destroyed. Stop quietly.
                    Log.d(TAG, "Splash wait interrupted, aborting navigation");
                    return;
                }

                // Touching the UI or starting an activity must happen on the UI thread.
                runOnUiThread(new Runnable() {
                    @Override
                    public void run() {
                        goToMain();
                    }
                });
            }
        });

        splashThread.start();
    }

    private void goToMain() {
        // isFinishing() protects us from navigating out of a dead activity.
        if (isFinishing() || isDestroyed()) {
            return;
        }
        Intent intent = new Intent(SplashActivity.this, MainActivity.class);
        startActivity(intent);
        finish();   // remove Splash from the back stack
    }

    @Override
    protected void onDestroy() {
        super.onDestroy();
        if (splashThread != null && splashThread.isAlive()) {
            // This is what throws InterruptedException inside sleep()
            splashThread.interrupt();
        }
    }
}

מה חשוב להבין לפני ההרצה?

  • Thread.sleep() – עוצר רק את ה-thread שקרא לו. זו בדיוק הסיבה שיצרנו thread נפרד: הוא זה שיישן, בזמן שה-thread הראשי ממשיך לצייר.
  • InterruptedException – זו חריגה מסומנת (checked): המהדר מסרב לקמפל בלי try-catch או throws. Java מכריחה אותנו לחשוב "מה קורה אם מישהו יקטע את ההמתנה".
  • runOnUiThread() – מתודה של Activity שמעבירה Runnable לתור של ה-thread הראשי. כל נגיעה ב-View או ניווט צריכה לעבור דרכה.
  • Intent – "מכתב כוונה" למערכת. new Intent(this, MainActivity.class) הוא Intent מפורש: אנחנו נוקבים בשם היעד.
  • finish() – מסיר את ה-Activity מה-back stack. בלעדיו, לחיצה על "חזור" מהמסך הראשי תחזיר את המשתמש למסך פתיחה שאין לו שום תפקיד.
  • interrupt() ב-onDestroy – מונע "thread זומבי" שמנסה לנווט אחרי שהמסך כבר מת. זה הרגל שיציל אותנו שוב בשלב 19.
